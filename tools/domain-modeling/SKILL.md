# 领域建模

这是**主动**的纪律：挑战术语、编造边界场景、在概念结晶的那一刻就把它写下来。

只为了查词汇而**读** `CONTEXT.md` 不算这个技能 —— 那是一行习惯，任何技能都该做。这个技能用在你要**改动**模型的时候，不是消费它的时候。

## 文件结构

多数仓库只有一个上下文：

```
/
├── CONTEXT.md          # 术语表，只有名词与定义
├── docs/adr/
│   ├── 0001-订单采用事件溯源.md
│   └── 0002-写模型用-postgres.md
└── src/
```

根目录若存在 `CONTEXT-MAP.md`，说明仓库有多个上下文，map 指向各自位置：

```
/
├── CONTEXT-MAP.md
├── docs/adr/                    ← 系统级决策
├── src/ordering/
│   ├── CONTEXT.md
│   └── docs/adr/                ← 该上下文的决策
└── src/billing/
    ├── CONTEXT.md
    └── docs/adr/
```

**懒创建**：有东西要写时才建文件。没有 `CONTEXT.md`，就在第一个术语被敲定时建；没有 `docs/adr/`，就在第一条 ADR 需要时建。

## 会话中的五个动作

**1. 对着术语表挑战**

用户用的词与 `CONTEXT.md` 里的既有定义冲突时，**当场指出**：「你的术语表把『取消』定义为 X，但你这里似乎指的是 Y。是哪个？」

**2. 磨锐模糊语言**

用户用含糊或超载的词时，提议一个精确的规范术语：「你说『账户』——指客户还是用户？这是两个不同的东西。」

**3. 讨论具体场景**

谈领域关系时，用具体场景压测它们。**编造**探测边界的情形，逼出概念之间的精确分界。

**4. 与代码交叉验证**

用户陈述某处如何工作时，**去代码里核对**。发现矛盾就挑明：「你的代码取消的是整张订单，但你刚说可以部分取消。哪个对？」

**5. 就地更新 CONTEXT.md**

一个术语被敲定，**当场**写进去。不要攒着批量写 —— 攒着写的那些，在写之前就已经开始漂移了。

`CONTEXT.md` **不含任何实现细节**。它不是规格书、不是草稿纸、不是实现决策的仓库。它只是术语表。

## ADR：三个条件全满足才写

1. **难以逆转** —— 以后改主意的代价是实在的
2. **脱离上下文会让人惊讶** —— 未来的读者会问"当初为什么这么做"
3. **是真实取舍的结果** —— 确实存在过别的选项，你为特定理由选了这一个

任一条不满足就跳过。三条都不缺才写，否则 ADR 目录会变成"我们做过的事"的流水账，没人会读。

## 反合理化表

| 借口 | 现实 |
|---|---|
| "意思大家都懂" | 懂的是各自脑子里的版本，它们不一样 |
| "先写完代码再统一术语" | 代码写完术语就固化了，改名的代价比现在高十倍 |
| "这个词历史遗留，别动" | 不动它就继续分裂 —— 术语漂移是复利 |
| "这条决策也值得记" | 记流水账的后果是整个目录失去可信度 |
| "CONTEXT.md 顺便写点实现说明" | 一旦混入实现细节，它就不再是术语表，而是第二份会过期的文档 |

## 完成判据

- 每个被敲定的术语都已写进 `CONTEXT.md`（不是记在对话里）
- 每条定义是**名词性的**，不含实现细节、不含"怎么做"
- 同一概念在代码、文档、对话里用**同一个词**
- 写下的 ADR 三条条件都成立，且含被放弃的选项与放弃理由
- 发现过但未解决的术语冲突被显式列出（留给下一次）
