# Retro（会话复盘）

## 核心

**复盘的对象不是「这次做得怎么样」，而是「agent 的环境该怎么改」。**

一次会话跑得顺不顺，取决于环境给了它什么：文件好不好找、错误能不能被自动抓到、
规矩写在哪、工具贵不贵。复盘就是**从这一次的具体经历里倒推出环境的改进点**——
下次同类任务不该再踩同一个坑。

所以复盘产出的是**对环境的改动提议**，不是对这次表现的评价。
「这次我搞错了」不是结论，「这里缺一个能自动抓到它的检查」才是。

## 步骤

### 1. 读一手材料

读用户指定的那次会话的**原始记录**（不是你的记忆、也不是别人转述的摘要）。
用户没指定就复盘当前这次。

跨会话复盘时，先确认材料确实读到了——**读不到就说读不到**，
不要凭印象编出一份"复盘"。

### 2. 按八个类别找改进点

| 类别 | 找什么 | 什么时候算命中 |
|---|---|---|
| **导航** | 文件之间有没有隐蔽依赖？加一个**导航指针**会不会更好找？ | 会话里为找一条信息花了很长时间 |
| **自动化检查** | 有没有本可以抓到错误的检查（lint / 类型 / 测试 / 文件系统检查）？ | agent 犯了一个自动化能抓的错，**或仓库根本没有 guardrail** |
| **编码标准** | reviewer agent 该不该多一条规则？现有规则要不要删/澄清？ | reviewer 漏掉了一个错 |
| **全局 AGENTS.md** | 有没有引导指令该挪进编码标准或自动化检查？ | AGENTS.md 特别长（仓库级或用户级） |
| **工具经济性** | 有没有昂贵的工具调用可以精简？某个 CLI / MCP 是否特别吃 token？ | 出现了昂贵的工具调用 |
| **无效指令** | 引导文件里有没有**根本不改变 agent 行为**的指令？ | 引导文件又长又难用 |
| **信息获取** | 能不能让 agent 多拿到一些信息（tee 开发服务器日志、第三方服务只读访问）？ | 某个关键信息 agent 拿不到 |
| **结果分层** | 检查点呈现的是**原始输出**还是**决策就绪的简报**？ | 人在检查点上还得自己从输出里找重点 |

### 3. 机械性 vs 判断题——这决定了改动落在哪

**这条判据是本节的全部价值**：拿到一个违规，先分类，再决定改哪。

- **机械性违规**（固定语法模式、被禁的 API、导入形状、文件位置规则）→
  **建确定性检查，没有例外**：仓库自己 linter 里的一条自定义规则、一个新的
  pre-commit hook、或一个新的 CI job——挑这个仓库的语言与现有 guardrail 里最省的那条。
  **默认建检查，而不是写规则。**
- **判断题**（跨文件一致性、「要和周围风格一致」、任何 guardrail 永远替代不了的东西）→
  才写进 `CODING_STANDARDS.md`。

**先读仓库自己的检查命令**（`package.json` / 构建工具的 `lint`/`check`、
CI workflow）：**「已经存在但没接上、或者已经悄悄坏掉的检查」才是发现，
而不是重新发明一个。** 一个既没有 pre-commit hook 也没有 CI job 跑 lint/类型/测试的仓库
**本身就是一个发现**——未 lint 的仓库是一个持续存在的错失机会，不是中性的默认状态。

### 4. 实现与评审的压力不对称

所有工作都过两阶段：实现和评审。

- **实现 agent 的上下文压力最大**——它要探索、写代码、调失败。
- **评审 agent 的压力最小**——它拿到的是一个 diff，不用探索，常常不用写代码或调试。

**推论：编码标准应该由评审 agent 施加，而不是实现 agent。**
把标准塞给压力最大的那个角色，只会让它更早开始走捷径。

### 5. 按严重程度呈现给用户

不要一次性倒出二十条。按「这条不改会怎样」排序，
**每条给出：位置、问题、建议的改法**。

## 反合理化

| 借口 | 现实 |
|---|---|
| 「这次是我疏忽，下次注意就行」 | 「下次注意」不可执行。同一个坑会再踩——把它变成检查。 |
| 「这个规则写进 AGENTS.md 就够了」 | 机械性的东西写成文字规则，等于要求每次都靠自觉执行；确定性检查才不依赖自觉。 |
| 「仓库里已有 lint，不用加了」 | 先确认它**真的在跑**。已存在但没接上/悄悄坏掉的检查是常态。 |
| 「复盘结论先记着，有空再改」 | 复盘的产出就是改动提议。不落地的复盘等于没做。 |
| 「这些改进点太多，挑重要的说」 | 「挑重要的」是判断，不是省略。给用户排序后的完整列表，让他决定砍哪些。 |
| 「凭记忆复盘就行，不用读原始记录」 | 记忆会把当时的困惑抹平成结论，正好抹掉最该复盘的部分。 |

## 与 auto-skills 台账的结合

复盘产出的每条改进点都值得留痕——下次同类会话有没有好转，靠它比对：

```bash
python scripts/auto_router.py trace retro "复盘: <会话标识> → 提炼 N 条环境改进（<改动落点>）" \
  --stage verify --status SUCCESS --query "复盘 环境改进" --project-root "<仓库路径>"
```

改动落地后追加一条，把「提议」和「落地」分开记：

```bash
python scripts/auto_router.py trace retro_apply "<改进项> → <落地形式: lint 规则/CI job/标准条目>" \
  --stage verify --status SUCCESS --query "复盘 落地" --project-root "<仓库路径>"
```

## 完成判据

- [ ] 读到了**一手材料**（原始会话记录），不是印象或二手转述
- [ ] 八个类别**逐个过了一遍**，明确说了哪些没命中（而不是只报命中的）
- [ ] 每条改进点都**分了类**（机械性 → 检查；判断题 → 标准文件）
- [ ] 每条都给了**位置 + 问题 + 建议改法**三要素
- [ ] 按严重程度**排序**后呈现，没有替用户砍掉他认为不重要的

以上任一条不满足，复盘就不算完成。

## 边界

- 只是想知道「这次改动对不对」→ 用 `code-review`，不是复盘。
- 想从历史日志里挖反复出现的模式 → 用 `experience_mining`（`auto_router.py exp`），
  那是跨会话的统计视角；复盘是**一次会话内的因果追溯**。
- 会话本身还没结束、问题还在发生 → 先 `systematic-debugging` 把问题定位掉，
  复盘等结束之后再做（否则你会把"正在发生的事"当成"已发生的事"来总结）。
