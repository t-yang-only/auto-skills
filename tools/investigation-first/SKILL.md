# 调查研究

> 没有调查，没有发言权。

调查是「实事求是」的入口：**不是为既定结论找材料，而是让事实规定判断**。

## 该用 / 不该用

该用：

- 要做决策，但对实际情况了解不够
- 面对陌生的代码库、系统或领域
- 别人的方案听起来合理，但你不清楚它的适用条件
- 发现自己在用"应该是""一般来说""通常"作答

不该用：

- 已经调查过，现在是执行阶段
- 用户已给出完整上下文和决策依据
- 答案跑一下就知道 —— 跑比查快

## 操作规程

1. **一句话写出调查目的**：「我要弄清楚的是：……」。没有目的的调查是漫游。
2. **列调查提纲**，覆盖四个面：
   - **现状**：现在是什么样（读源码、配置、数据，不只看文档）
   - **历史**：为什么变成这样（`git log`、`git blame`、变更记录）
   - **关联**：牵涉哪些约束（接口、依赖、调用方、部署环境）
   - **多方**：有哪些不同说法（文档 vs 代码 vs 运行结果 vs 用户描述）
3. **亲自接触第一手材料**：直接读、直接跑、直接看日志。二手总结只能当线索，不能当证据。
4. **边查边记，分三栏**：每条发现标来源；把"看到的"和"推出来的"分开。
5. **先出结论，再谈方案**：调查结论必须先于任何行动方案，不得边查边给方案。
6. 事实与预期不符时，**改判断，不改事实**。查不清的，诚实写"未知"。

## 输出模板

```text
调查目的：……
调查范围：读了 …… / 跑了 …… / 问了 ……

已核实的事实（附来源）：
- ……（来源：文件:行 / 命令输出 / 日志）
合理推断（说明推理链）：
- ……（因为 …… 所以 ……）
未知 / 存疑：
- ……（需要 …… 才能确认）

调查结论：
- 现状是：……
- 关键约束是：……
- 我原来不知道、现在知道的是：……
- 基于以上，我的判断是：……（置信度：高 / 中 / 低）
```

## 与 auto-skills 台账的结合

调查是**认领任务后的第一个动作**，不是可选的：

- 认领任务时（`nm-skills` 的 `claim`）记下调查目的与范围，它就写在任务卡上
- 调查中发现范围比声明的大 —— **改 `--files` 声明**，而不是默默扩大改动面
- 调查结论落进台账，后续 review 才有依据判断"这个改动是否解决了它声称要解决的问题"：

```bash
python scripts/auto_router.py trace investigation_first "调查: <目的> → <结论摘要>" --stage understand --status SUCCESS --query "<关键词>" --project-root "."
```

## 纪律

- **未知栏非空且关系到结论时，不得下定论** —— 要么补查，要么把不确定性写进结论
- **走马观花不算调查** —— 只看目录结构和 README 就总结，是最常见的假调查
- **调查有预算** —— 先写提纲，按提纲查完即止；发现新的大问题另开一轮，不无限扩张
- **改判断不改事实** —— 预期与事实冲突时，先怀疑预期

## 交接

- 调查揭示多头矛盾、抓不住重点 → `contradiction-analysis`
- 结论已形成、需要验证 → `verification-before-completion`
- 范围大、可分头查 → 派后台 agent 并行调查，主线只汇总三栏
- 需要查的是外部资料而非本仓库现状 → `research`

## 完成判据

- 三栏齐备（事实有来源、推断有推理链、未知有"需要什么才能确认"）
- 调查目的与范围可复述，且范围内的问题都已有结论或明确标为未知
- 结论先于方案；未出现"边查边给方案"的混写
