# 写给 Agent 的文档

同一批杠杆让每份文档都变得**可预测**。注意措辞：不是"产出同样的输出"，而是 agent 每次运行走的是**同一个过程**。你写的不是一篇说明文，是一段会被反复执行的**过程约束**。

适用于任何 agent 消费的文档：SKILL.md、`AGENTS.md` / `CLAUDE.md`、被指针引到的 doc。包装不同，写法相同。

## 1. 上下文指针：措辞决定触发

**上下文指针** = agent 上下文里持有的一个引用，它命名某份上下文之外的材料，并编码**到达该材料的条件**。技能的 `description` 是一个指针；`AGENTS.md` 里一行指名的 doc 是同一个对象。

关键结论：**决定 agent 何时到达、以及多可靠地到达的，是指针的措辞，不是它的目标**。

一个必须到达的目标挂在措辞软弱的指针后面 = **variance bug**（同一次运行触发、下一次不触发）。处理顺序是固定的：**先磨措辞；只有磨不动才把材料内联进来**。

指针干两件事：

- 说明**材料是什么**
- 列出应触发到达它的**分支**（branch = 文档处理的某个独立情形，不同运行会走不同路径）

两条纪律：

- **把引领词前置** —— 指针正是它发挥触发作用的地方，开头几个词承担全部触发责任
- **每个分支一个触发词** —— 给同一个分支起同义词只会稀释触发强度

## 2. 两种负载

每份文档和每个指针都在花两种预算之一：

- **上下文负载**（context load）= 常驻材料对 agent 窗口的成本。`AGENTS.md` 一行、一个技能 description、任何坐在上下文里的东西。**常驻的每个词每一轮都在付费**
- **按需加载** = 只能通过指针到达的材料，代价是它自己那一行

没有任何指针的材料，则完全靠自身承载（进了上下文就再也出不去）。

## 3. 信息层级

文档由两类内容构成：**步骤**（agent 按序执行的动作）与**参考**（按需查阅的定义、规则、事实）。三级阶梯：

1. **文件内步骤**是主层：agent 按序做什么
2. **文件内参考**按需查阅（常常是合法的一长段平坦清单）
3. 更下层：移出主文件、放到指针后面

**推得太少顶部臃肿；推得太多把 agent 真需要的材料藏起来 —— 这个张力就是全部决策。**

- **渐进披露**（progressive disclosure）= 沿阶梯向下移动，目的是让**顶部保持可读**，不是为了省 token
- **同位**（co-location）= 文件内的配套动作：阶梯决定一块内容坐得**多深**，同位决定它旁边**坐着谁**
- **蔓延**（sprawl）是这里的失败模式：文档单纯太长 —— 即使每一行都是活的、独一无二的。**注意力在过量中变薄**

## 4. 步骤与完成判据

每个步骤都以一个**完成判据**结束，它告诉 agent 活干完了。两个性质使它成为杠杆：

- **清晰**：agent 能否分辨做完 / 没做完？模糊的边界（如"理解已达成"）会招致 **premature completion**（在前置步骤真正完成前就结束它）
- **穷尽**：判据要覆盖"所有该做的都做了"，而不只是"某一件做了"

**最强的判据同时可检验且穷尽。** 判据写成能跑的命令、能看的输出、能数的条目，而不是形容词。

## 5. 何时拆分

把一份文档拆成两份要花掉两种负载之一，所以只在切得值时才切：

- **按序列拆**：把一串步骤拆开，当"完成后才该做的步骤"会诱使 agent 赶工它前面那一步时 —— **让它们不在视野里能驱动顺序正确**

反面：为了"看起来整洁"按主题拆，会让 agent 在多个文件间跳，反而丢上下文。

## 6. 引领词

**引领词** = 一个紧凑概念，已存在于模型的预训练中，agent 运行文档时用它来思考（_lesson_、_focus_、_tight_、_red_ 之类）。

它**锚定两次**：

- 在正文里锚定**执行**：每次出现该词，agent 都伸手取同一个行为
- 在平坦参考里锚定**聚焦**：它把注意力收拢

要主动寻找用引领词重构的机会：同一个三件套在三处被拼写出来、一个指针花一整句去指一个概念。例子：

- "fast, deterministic, low-overhead" → **_tight_**（a _tight_ loop）
- "a loop you believe in" → **_red_**，把一个模糊的闸门变成二元可观察状态

**赢两次**：更少 token + 给 agent 一个更锐利的挂靠点。假设每份文档都带着可以被引领词替换的复述。

## 7. 修剪：禁止是失败模式

**Negation 是这条杠杆旁边的失败模式** —— **靠禁止来引导，会把被禁止的行为拖进上下文，并让它变得更可得（_more_ available）**。

写"不要做 X"时，X 本身被写进了 agent 的上下文，成为它思考时的候选之一。纯禁止式清单越长，被禁行为的在场感越强。

**替换法**：把"不要做 X"改写成"做 Y（Y 是 X 的正面替代）"。判据是**这条规则能不能被一个动作直接执行** —— 能，就是正面表述；只能靠"忍住不做"来满足，就是禁止式。

**单一真相源**：每个含义只保留一个权威位置，改行为就是改一处。**重复是失败模式** —— 同一规则写在三处，三处迟早不一致，而 agent 会按它最后读到的那处执行。

## 应用到 auto-skills 自身

本仓库已有三处机制正好对应上述杠杆，改动它们时按同一套判据：

- **`description` 的触发词**：`_test_registry.py` 的第 12 段用 `TRIGGER_RE` 校验每个技能描述含触发条件、长度 ≥60、且不自带弱表述。这正是"指针措辞决定触发"的机械化落地 —— 加技能时不要绕过它
- **`template/SKILL.md`**：新技能的骨架。骨架决定了默认的信息层级（步骤在前、参考在后）
- **`references/capability-map.md`**：渐进披露的实例 —— 35 个技能的能力全景在一份文件里，细节留在各自 SKILL.md

写新技能时的最小自检：description 里有没有**分支枚举**？步骤有没有**完成判据**？规则是正面表述还是禁止式？有没有把同一含义写了两遍？

## 完成判据

- 文档开头能一眼看出"什么时候该读它"（指针措辞可触发）
- 每个步骤都有可检验的完成判据
- 没有纯禁止式规则（禁止已改写成正面动作）
- 同一含义只在一个地方定义
- 新增内容没有把主文件推到"蔓延"（主文件仍是可读的步骤层，参考已下沉）
