# 一手来源调研

二手转述会失真，而且**失真的方向通常是"变得更确定"** —— 一篇博客会写"X 一定支持 Y"，而官方文档写的是"Y 在 Z 条件下支持"。调研的产出质量，取决于你走到了链条的第几环。

## 谁来做

**派后台 agent 去读，自己继续干活** —— 调研是典型的"读得多、写得少"任务，串行等待是纯浪费。

DSH 里用 `subagent` 派后台子代理；Codex / Claude Code 里用各自的后台任务机制。给它的指令要自包含（它看不到你的对话）。

## 三件事

**1. 对着第一手来源查**

官方文档、源码、规范、第一方 API —— 不是它们的二手转述。**每条声明都要回溯到拥有它的那个源头**。

判断标准：如果某个说法只能在一篇博客或问答里找到，它是待验证的，不是结论。

找不到一手来源时**如实标注**：「未找到官方说明，以下来自社区实践」——这比含糊地写成事实有用得多。

**2. 写进一个 Markdown 文件**

每条声明后面跟来源（URL / 文件路径 + 行号 / 命令输出）。

文件里同时记录**查过但没找到的** —— 下一个人的第一反应是去查同一个地方。

**3. 存在仓库已有的位置**

先看仓库怎么放这类笔记（`docs/`、`notes/`、`research/`），**沿用既有约定**；没有约定就选个合理位置，**并说明放在哪了**。

## 反合理化表

| 借口 | 现实 |
|---|---|
| "我记得是这样" | 记忆的时效性未知，而且它不会告诉你自己过期了 |
| "搜索结果第一条就这么说" | 搜索排名不等于权威性，官方文档常在第 3 位之后 |
| "文档太长，看摘要吧" | 摘要丢掉的往往正是适用条件 |
| "博客写得比文档清楚" | 清楚不等于准确 —— 博客可以跳过边界条件 |
| "先写结论，来源稍后补" | "稍后"不会到来，而没有来源的结论无法被复核 |

## 完成判据

- 每条声明都能追到一个一手来源（URL / 文件路径 + 行号）
- 无法溯源的部分被显式标注为「社区实践 / 待验证」
- 产出是**一个**文件，不是散落的聊天记录
- 文件位置符合仓库既有约定，或已在文件里说明为何放在这里
- 查过但无果的路径也被记下来
